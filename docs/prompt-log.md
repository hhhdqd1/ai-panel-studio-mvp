# 核心 Prompt 案例

以下六段是依据 AI Panel Studio 已完成的设计、代码、测试与验收结果整理出的**开发 Prompt**，用于展示如何分阶段引导 AI 完成项目。阶段标签分别对应 SDD（规格驱动）、DDD（设计驱动）、TDD（测试驱动）和 E2E（系统验收）。实际开发助手为 Codex，应用运行时接入 DeepSeek API，默认模型 ID 为 `deepseek-chat`；不声称使用过 Claude Code 或未经核实的模型版本。

1. **【SDD 阶段】数据建模与 API 契约生成｜建立可恢复的领域模型**
**Prompt｜角色与背景：** 你是负责交付 AI 圆桌讨论 Web App MVP 的后端架构师。用户输入 1–500 字议题，确认 1 位主持人和 2–6 位不同立场的专家后开始讨论；页面必须能实时展示发言、刷新恢复，并允许多场讨论相互隔离。请先把这些业务描述转换为可验证的不变量，不要直接从页面组件倒推数据库字段。
**Prompt｜执行要求：** 定义 `discussion`、`agent`、`message`、`insight`、`event`、`model_run` 六类实体的主键、关联、字段、约束与索引；列出讨论状态机和允许的转移，说明五条预设议题如何幂等导入。给出 SQLite WAL 下写入发言、洞察与递增事件序号的事务边界，并解释读取快照时怎样保证 `last_event_seq` 与内容处于同一一致性视图。
**Prompt｜交付与验收：** 输出 ER 图、状态转移表、字段说明、失败恢复边界和至少 8 条可执行的验收条件；逐条标注哪些是已确认需求、哪些是为 MVP 作出的设计假设。遇到冲突先列出取舍，不要把未运行的方案写成已验证事实。
> 说明：这段 Prompt 的意图是先固定持久化与恢复语义，避免界面完成后才发现状态无法回放。实际挑战是快照与事件并发写入可能造成重复展示，因此需要引导 AI 明确读事务和事件序号的一致性约束。

2. **【SDD 阶段】数据建模与 API 契约生成｜约束模型网关与实时接口**
**Prompt｜角色与背景：** 在上述领域模型上，请以 API 设计负责人身份制定前后端共同遵守的契约；运行时模型提供方为 DeepSeek，但浏览器只能访问本地后端，不能接触 `DEEPSEEK_API_KEY`、模型内部推理或原始未校验响应。
**Prompt｜执行要求：** 为创建讨论、获取列表与快照、确认阵容后开始、失败后恢复、按 `after` 序号订阅 SSE 定义请求、响应、状态码和错误码。明确议题长度、专家人数、阵容结构和模型 JSON 的校验规则；区分可重试的超时或限流、不可重试的结构错误、已耗尽调用预算。提供显式 `APP_FAKE_MODEL=1` 的可复现演示路径，同时定义真实网关的超时、有限重试与调用日志，不把 API Key 写入前端、数据库或提交包。
**Prompt｜交付与验收：** 产出 OpenAPI 可落实的接口表、示例 payload、SSE 事件类型、错误矩阵及网关测试清单。要求刷新时先读取一致性快照，再从 `last_event_seq` 后续接事件；重复序号去重，出现跳号则重取快照，断线不得把旧内容清空。
> 说明：这段 Prompt 要解决“模型能调用”与“产品能稳定运行”之间的落差，把密钥安全、结构校验和事件补发写成接口契约。修正方向是让模型网关与浏览器协议分别承担失败处理，避免把超时或 SSE 重连误当作讨论完成。

3. **【DDD 阶段】前端组件与页面生成｜构建有圆桌语义的实时界面**
**Prompt｜角色与背景：** 你是 React + TypeScript 前端设计工程师。请把 AI 圆桌讨论呈现为“可观看的演播厅”，而不是通用聊天列表：主持人和专家围绕桌心就座，用户能在开场前确认姓名、职业、立场与专长，开场后一眼看到谁在举手、谁正在发言、当前主持人问题是什么。
**Prompt｜执行要求：** 拆分首页、阵容预览、圆桌席位、实时记录、讨论洞察和总结组件，建立由服务端快照与 SSE 事件驱动的单一页面状态。当前发言席位使用明显高对比填充与光晕，不能只改细边框；风险条目可跳转并高亮对应原发言。桌面端同时显示圆桌、记录、洞察；约 390px 手机端使用“圆桌／记录／洞察”标签切换，并保留可读字号、键盘焦点和状态文字。
**Prompt｜交付与验收：** 输出组件职责、状态映射、关键交互和样式实现；分别检查待确认、讨论中、审查不可用、断线重连、已完成等状态。用 1440px 与 390px 实际浏览器截图核验当前发言高亮和风险定位；不要以静态设计图代替运行页面。
> 说明：意图是让“圆桌”成为信息结构而不只是装饰，并让实时状态在宽屏和手机上都清楚可见。实际挑战是主持人席位样式曾压过发言高亮，需要引导 AI 通过浏览器检查 CSS 优先级并修正对比度。

4. **【TDD 阶段】核心逻辑的测试用例编写与业务实现｜实现自主发言编排**
**Prompt｜角色与背景：** 你是编排逻辑负责人。专家不能机械轮流发言：每轮应先基于同一可公开上下文独立提交举手意愿和简短理由，再由确定性的选择器结合相关性、新颖度、紧迫度与发言公平性选出发言者；主持人负责开场、追问、转场和总结。
**Prompt｜执行要求：** 先写失败测试，再实现最小通过代码，最后重构。测试至少覆盖：未确认阵容不得开场；专家意愿并发收集但讨论之间隔离；选人不会长期偏向同一专家；举手与清除状态确实进入事件流；专家发言限制为 1–2 句；全体连续拒绝或意愿调用失败时暂停并可恢复；六专家场次提前为总结和一次失败重试预留调用额度，整场最多 100 次模型调用、20 分钟。
**Prompt｜交付与验收：** 分别给出测试用例表、关键状态转移、编排器接口和实现；每个失败路径必须说明已保存内容是否保留、用户能否恢复、预算耗尽时展示什么。运行完整后端测试，并记录真实失败用例与修正，不得把假模型的稳定输出等同于真实 DeepSeek 的生成质量。
> 说明：这段 Prompt 把“自主讨论”的体验要求转为可测的选择与恢复规则。实际挑战包括早期举手状态没有发布，以及六专家讨论可能耗尽预算；因此引导 AI 先复现边界失败，再调整事件发布和预算预留。

5. **【TDD 阶段】核心逻辑的测试用例编写与业务实现｜限制幻觉风险标记的证据边界**
**Prompt｜角色与背景：** 你是负责讨论审查的工程师，但系统没有外部权威数据库，不能把模型评价写成事实核查结论。目标是发现值得追问的断言，并让用户直接回到发言原文，而不是给人物或观点贴“真／假”标签。
**Prompt｜执行要求：** 先为 `sanitize_review` 与洞察合并写失败测试：仅接受“记录冲突、来源未提供、需外部核实”三类原因；每条风险必须含已持久化的 `message_id` 和该发言中真实出现的 `quote`；纯观点、虚构消息 ID、与原文不符的引用应被过滤。新增一轮审查不得抹掉尚未解决的既有风险；审查失败时保留发言并记录“本轮审查暂不可用”，刷新后仍可看到未审查状态。
**Prompt｜交付与验收：** 实现结构化模型输出、服务端二次校验、状态持久化及前端“查看原发言”定位；提交单元测试、API 测试与浏览器交互测试。文案必须持续声明“风险提示不等于真伪判定”，不要生成不存在的来源，也不要因审查失败删除讨论内容。
> 说明：意图是把“幻觉检测”收敛成有证据链的风险提示。挑战是审查模型本身也可能编造引用，所以修正重点是服务端核对消息 ID 和原句，并把审查不可用作为显式状态呈现。

6. **【E2E 阶段】系统级端到端测试与质量闭环｜验证完整用户旅程**
**Prompt｜角色与背景：** 你是交付前的质量负责人。请从真实浏览器操作出发验证 MVP，不要只依据单元测试或静态截图宣称完成；默认使用显式假网关保证可重复与零 API 费用，真实 DeepSeek 冒烟检查单独记录。
**Prompt｜执行要求：** 用 Playwright 覆盖“选择预设／输入自定义议题 → 查看并确认阵容 → 主持人开场与专家发言 → 实时洞察与风险定位 → 结束总结”的主路径；加入刷新后的快照与 SSE 补发、重复事件去重、断线提示与恢复、两场并发隔离、失败检查点恢复。分别在桌面和约 390px 手机视口检查发言高亮、标签切换与定位；对发现的缺口先添加复现用例，再修复并回归。
**Prompt｜交付与验收：** 输出测试矩阵、运行命令、通过／失败结果和三张来自实际浏览器的截图；另运行后端测试、前端单测与构建，并检查提交包不含 `.env`、API Key、SQLite 运行库或依赖目录。真实 API 冒烟只记录实际观察到的响应、耗时与风险，不得用假网关结果冒充真实模型表现，也不要自动发送邮件或创建虚构仓库链接。
> 说明：意图是把“能运行”提升为“可复现、可恢复、可交付”的证据链。实际挑战跨越浏览器、实时事件和后端任务状态，因此用独立假网关测试工程行为，并把真实 API 质量检查单列，避免混淆两类结论。
